# Ludovanta

Платформа для AI-first разработки игр на Unity.

Обвязка для AI-first разработки на Unity: скиллы и инструкции для агентов (Claude Code, Codex и
другие, в том числе запущенные из ADE вроде Orca), команды headless-проверок проекта и безопасный
механизм установки/обновления платформы в игровые проекты.

Платформа не вмешивается в Unity: всё работает снаружи через batchmode Unity, официальный Unity MCP
(когда открыт Editor) и файлы в репозитории проекта.

Требования: **Python 3.9+** (только стандартная библиотека, без pip-зависимостей), git, Unity через
Unity Hub. Работает на Windows, macOS и Linux.

## Что ставится в Unity-проект

```
<project>/
  .ludovanta/                           # принадлежит платформе, заменяется целиком при обновлении
    ludovanta.py                        #   единая точка входа: status | compile | test | test-audit | validate-assets | plan | codex | feedback | update
    ludovanta_lib/                      #   реализация команд
    hook.sh                             #   запуск хуков Claude Code (ищет Python 3.9+)
    lock.json                           #   установленная версия + хэши всех файлов платформы
  .claude/skills/ludovanta-*/SKILL.md   # скиллы платформы для Claude Code
  .agents/skills/ludovanta-*/SKILL.md   # те же скиллы для Codex (папки задаются в skillTargets)
  .claude/settings.json                 # + хуки Ludovanta (SessionStart, Stop), остальные настройки ваши
  AGENTS.md                             # + блок ludovanta:managed с правилами для агентов, остальной текст ваш
  CLAUDE.md                             # + блок ludovanta:managed с импортом @AGENTS.md, остальной текст ваш
  .gitignore, .gitattributes            # + управляемый блок ludovanta:managed
  ludovanta.json                        # ваш: откуда и какую версию платформы брать
  ludovanta.local.json                  # ваш, в .gitignore: настройки конкретной машины
  plan/                                 # ваш (создаёт `plan init`): цель, дизайн игры, майлстоуны, карточки задач
  docs/feedback-log.md                  # ваш (создаёт `feedback add`): журнал трения
```

Команды (из корня проекта; на Windows `python` или `py -3` вместо `python3`):

```
python3 .ludovanta/ludovanta.py status            # LIVE (открыт Editor) или HEADLESS, найден ли Unity
python3 .ludovanta/ludovanta.py compile           # компиляция в batchmode, компактный список ошибок
python3 .ludovanta/ludovanta.py test [--platform EditMode|PlayMode] [--filter X] [--category Y] [--repeat N]
python3 .ludovanta/ludovanta.py test-audit        # хрупкие, медленные и нестабильные тесты, без запуска Unity
python3 .ludovanta/ludovanta.py validate-assets   # .meta / GUID без запуска Unity
python3 .ludovanta/ludovanta.py plan              # план проекта: прогресс, задачи на проверке, следующие задачи
python3 .ludovanta/ludovanta.py plan next|check|init|add-milestone|add-task|set|fail
python3 .ludovanta/ludovanta.py plan brief [T-001]   # сводка для новой сессии или для исполнителя задачи
python3 .ludovanta/ludovanta.py plan close [--carry] # закрыть выполненный план в plan/archive/
python3 .ludovanta/ludovanta.py plan stats           # по агентам: принято задач, с первой попытки, неудачные попытки
python3 .ludovanta/ludovanta.py codex run T-001      # отдать задачу Codex CLI
python3 .ludovanta/ludovanta.py codex image "описание" --out Art/References/hero.png   # референс через Codex
python3 .ludovanta/ludovanta.py feedback add "что мешает" --doing "что делали" --severity 1|2|3
python3 .ludovanta/ludovanta.py feedback show [--days 7]  # журнал трения для еженедельного разговора
python3 .ludovanta/ludovanta.py update [--ref vX.Y.Z] [--dry-run] [--force]
```

У всех команд есть `--json`. Коды выхода общие: `0` ок, `1` проблемы в проекте (ошибки компиляции,
упавшие тесты, битые ассеты), `2` проблема окружения (Unity не найден, лицензия, падение),
`3` проект открыт в другом экземпляре Unity, `4` таймаут.

Скиллы:

| Скилл | Когда агент его использует |
|---|---|
| `ludovanta-game-design` | новая игра или большая фича: фантазия, основной глагол, прогон сессии, game feel, арт-направление и уровень проработки графики в `plan/design.md`; жалоба «скучно / сыро» |
| `ludovanta-design-review` | критик качества игры: план перед показом пользователю, первая играбельная версия, конец майлстоуна, «почему скучно» |
| `ludovanta-unity-compile` | после изменений C#/asmdef/пакетов, разбор ошибок компиляции, live-режим через Unity MCP |
| `ludovanta-unity-test` | тесты как самопроверка агента: запуск и написание EditMode/PlayMode тестов, какой тест хороший, нестабильные тесты и карантин, аудит набора тестов |
| `ludovanta-plan` | планирование и декомпозиция, прогресс, оркестратор и исполнители задач, handoff и новые сессии, закрытие плана, остановка после 3 неудачных попыток |
| `ludovanta-feedback` | «запиши, что неудобно»: запись в журнал трения `docs/feedback-log.md` и сводка за неделю |
| `ludovanta-codex` | Codex CLI как исполнитель небольших задач (`agent: codex`) и генератор картинок-референсов |
| `ludovanta-unity-assets` | создание/перенос/удаление ассетов, .meta и GUID, правила для сцен и префабов |
| `ludovanta-platform-update` | обновление платформы, разбор конфликтов в файлах платформы |

## План и карточки задач

План проекта лежит в самом проекте и коммитится вместе с ним (папка задаётся в `ludovanta.json` → `"planDir"`,
по умолчанию `plan/`):

```
plan/goal.md              # что делаем, что входит и не входит, когда готово
plan/design.md            # как игра играется, ощущается и выглядит; в заголовке `fidelity`
plan/milestones/M1.md     # майлстоуны по порядку
plan/tasks/T-001.md       # одна карточка на задачу; раздел `## Handoff` пишет исполнитель для следующих задач
plan/handoff.md           # сводка для следующей сессии: где мы, что дальше, что сказал пользователь
plan/archive/01-<план>/   # закрытые планы с SUMMARY.md; команда `plan` их не читает
```

У карточки есть заголовок (`id`, `title`, `milestone`, `status`, `agent`, `size`, `depends`, `attempts`) и
свободный текст на любом языке. Каждая строка `- [ ] ...` в тексте считается критерием приёмки. Платформа
следит за контрактом задачи:

- задачу нельзя взять в работу (`in-progress`, `review`, `done`) без критериев приёмки;
- агент переводит задачу в `review` и отчитывается по критериям, а `done` ставится после приёмки
  человеком;
- `plan fail` записывает неудачную попытку в журнал карточки. После трёх неудач подряд (`"maxAttempts"` в
  `ludovanta.json`) команда отвечает `STOP`, и агент должен остановиться и задать вопрос, а не
  переделывать в четвёртый раз;
- прогресс считается с весами по размеру задачи (S=1, M=2, L=4), задачи на проверке показываются отдельно.

Компиляция и тесты — это нижняя планка, а не цель: платформа ведёт агента к игре, в которую интересно
играть. До плана агент делает дизайн-проход (скилл `ludovanta-game-design`) и спрашивает уровень
проработки графики (`prototype`, `stylized`, `high`, `max`, `reference`) вместо заглушек по умолчанию.
Первый майлстоун — первая играбельная версия: основной глагол с обратной связью, а не прогулка по
greybox. У задач с геймплеем есть критерии ощущения (эффекты, звук, реакция мира). Критик
(`ludovanta-design-review`) проверяет план и первую играбельную версию. `plan check` предупреждает,
если `design.md` нет или уровень проработки не выбран, а `plan` показывает выбранный уровень.

Распределение между агентами задаёт поле `agent` (`claude`, `codex`, `any` или человек), а
`plan next --agent codex` выдаёт задачи, готовые для конкретного агента. Взяв задачу, исполнитель
записывает себя в `agent`, поэтому `plan stats` показывает по каждому агенту, сколько задач принято,
сколько с первой попытки, сколько было неудачных попыток и остановок, с учётом закрытых планов. Правила
распределения проекта записываются в `AGENTS.md` вне блока платформы и пересматриваются по этим цифрам.

### Длинные планы и контекст

Сессия, которая говорит с пользователем, работает как оркестратор: каждую задачу она отдаёт исполнителю
со свежим контекстом (субагенту Claude или Codex) и читает только его короткий отчёт. Исполнитель получает
всё нужное одной командой `plan brief T-xxx`: дизайн, карточку, handoff зависимостей и правила. Поэтому
контекст оркестратора растёт на килобайты за задачу, а не на весь написанный код.

Решения хранятся в файлах плана, а не в чате, так что новая сессия ничего не теряет. Хуки Claude Code,
которые ставит Ludovanta:

- **SessionStart** (новая сессия, `/clear`, компрессия): кладёт в контекст `plan brief` и `plan/handoff.md`;
- **Stop** (после каждого ответа): если только что закрыта веха и контекст больше 100k токенов (или закрыта
  любая задача при контексте больше 300k), просит агента записать `plan/handoff.md` и предложить
  пользователю `/clear`. Пороги: `ludovanta.json` → `"handoff": {"milestoneTokens": 100000, "taskTokens": 300000}`.

Сам сбросить контекст хук не может, поэтому `/clear` набирает пользователь. После этого достаточно
написать «продолжай». Отключить хуки: `"claudeHooks": false` в `ludovanta.json` и `update`.

### Когда план выполнен

`plan` пишет PLAN_COMPLETE. `plan close` переносит `goal.md`, `handoff.md`, майлстоуны и задачи в
`plan/archive/NN-<название>/` и пишет там `SUMMARY.md` (статистика и место для ретроспективы).
`design.md` остаётся: он живёт всю жизнь игры. Нумерация задач и майлстоунов продолжается, задачи
закрытых планов считаются выполненными зависимостями. Незакрытые задачи можно перенести в следующий
план (`--carry`). Следующая итерация начинается с дизайна (скилл `ludovanta-game-design`), потом
`plan init --title "..."`.

### Codex

Codex CLI подключается как второй агент: исполнитель небольших задач (`agent: codex`) и генератор
картинок-референсов по подписке ChatGPT (встроенный `$imagegen`). `status` показывает, найден ли
`codex`. `codex run T-xxx` передаёт задачу в `codex exec` через файл с брифом (без длинных аргументов
командной строки, которые ломает cmd.exe) и печатает короткий отчёт и изменённые файлы. Настройки:
`ludovanta.json` → `"codex": {"sandbox": "workspace-write", "model": "..."}`, путь к исполняемому файлу:
`ludovanta.local.json` → `"codexPath"` или `CODEX_PATH`.

### Одни правила для Claude и Codex

Правила платформы лежат прямо в управляемом блоке `AGENTS.md`: Codex читает этот файл сам, а
`CLAUDE.md` импортирует его (`@AGENTS.md`). Поэтому оба агента, в том числе запущенные из Orca,
видят одни и те же правила и одни и те же настройки проекта. Скиллы ставятся в `.claude/skills` и в
`.agents/skills` (по умолчанию для новых установок). В проектах, установленных раньше, добавьте
`.agents/skills` в `skillTargets` и запустите `update`. Если Codex найден, а скиллов для него нет,
`status` об этом предупреждает.

Настройки проекта, например язык и подробность отчётов или правила распределения задач, пишутся в
`AGENTS.md` вне блока платформы. Агент сам добавляет туда строку, когда пользователь просит что-то
делать всегда. Не стоит писать их в `CLAUDE.md` или `ludovanta.local.json`: Codex и новые worktree их
не увидят. Пример:

```markdown
## Preferences

- Язык: отвечай и пиши карточки по-русски, технические термины по-английски. Коротко, без объяснений основ.
- Codex: задачи размера S без работы со сценой. Всё со сценами, префабами и Unity MCP делает Claude.
```

### Тесты: самопроверка агентов

Тестами занимаются только агенты. Пользователь их не пишет, не запускает и не проверяет. Тестов нет
ни в критериях приёмки, ни в задачах плана, а в отчёты пользователю детали тестов не попадают.

- `test` перезапускает упавшие тесты один раз (до 5 штук). Если тест прошёл без изменений кода, он
  нестабильный: команда отвечает `TESTS_FLAKY` с кодом 0, а не `TESTS_FAILED`, и агент не пытается
  «чинить» то, что не ломал.
- Карантин: тесты с `[Category("Flaky")]` запускаются и видны в каждом результате, но их падения не
  проваливают прогон. Агент чинит их позже и снимает категорию, когда `test --filter X --repeat 5`
  отвечает `TESTS_STABLE`.
- `test --repeat N` прогоняет одни и те же тесты N раз и делит их на нестабильные и падающие всегда.
- `test-audit` без запуска Unity ищет признаки плохих тестов: рефлексию в приватные поля, ожидание в
  реальном времени, случайность без seed, точное сравнение float, поиск объектов по имени,
  `[Ignore]` и карантин, медленные тесты, тесты, которые часто падали в последних прогонах, файлы
  тестов, переписанные много раз за 30 дней, и игровой код вне `.asmdef`. Оркестратор запускает аудит
  в конце майлстоуна и отдаёт чистку исполнителю без карточки в плане.
- Каждое изменение ожиданий теста, `[Ignore]`, карантин или удаление записывается в `## Log` карточки
  задачи, а оркестратор проверяет такие правки.
- **Гейт.** `test` запоминает каждый полный прогон (без `--filter` и `--category`) по платформам в
  `Logs/ludovanta/test-state.json`. `plan set --status review` отказывает с `TESTS_NOT_GREEN`, пока у
  каждой платформы, где есть тестовая сборка, нет зелёного полного прогона, начатого после последней
  правки кода (`.cs`, `.asmdef`, `.asmref`, `Packages/manifest.json`). Нестабильные тесты и тесты в
  карантине не блокируют, проекты без тестовых сборок проходят. Если Ludovanta не может запустить Unity
  (открыт Editor, песочница Codex), агент пишет `--unverified "почему и что проверил вместо этого"`.
  Это попадает в журнал карточки, и оркестратор прогоняет тесты сам до отчёта пользователю.

### Журнал трения

Фраза агенту «запиши, что неудобно» добавляет строку в `docs/feedback-log.md` (скилл
`ludovanta-feedback`): дата, что делали, что помешало, сила от 1 до 3. Перед еженедельным разговором
`feedback show` выводит записи за неделю, самые серьёзные сверху. Файл принадлежит проекту и только
дописывается, а `.gitattributes` сливает его с `merge=union`, поэтому записи из параллельных worktree
не конфликтуют.

## Установка в проект

```
git clone <url-этого-репозитория> ludovanta
python3 ludovanta/install.py --project /path/to/MyGame --source <url-этого-репозитория> --ref v0.1.3
```

`--source` и `--ref` записываются в `ludovanta.json` проекта и дальше используются для обновлений.
Установку стоит закоммитить отдельным коммитом (скрипт подсказывает команду).

## Обновление

Из корня игрового проекта:

```
python3 .ludovanta/ludovanta.py update --dry-run       # что изменится
python3 .ludovanta/ludovanta.py update                 # до версии из ludovanta.json
python3 .ludovanta/ludovanta.py update --ref v0.2.0    # на другую версию (обновит ludovanta.json)
```

`update` клонирует нужный тег во временную папку и запускает **установщик новой версии**: логика
миграции всегда берётся из версии, на которую обновляемся. Откат на старую версию работает так же.

Коды выхода: `0` готово, `1` найдены локальные изменения файлов платформы (ничего не записано),
`2` ошибка.

## Почему обновления не создают проблем с мержем

1. **Чёткое владение файлами.** Всё в `.ludovanta/` и `<skills>/ludovanta-*` принадлежит платформе и пишется
   только установщиком. В общих файлах (`AGENTS.md`, `CLAUDE.md`, `.gitignore`, `.gitattributes`)
   платформа владеет только одним блоком между маркерами `>>> ludovanta:managed` и `<<< ludovanta:managed`.
   Остальное принадлежит проекту, и установщик это не трогает.
2. **Детерминированный результат.** Одна и та же версия всегда даёт одинаковые байты: LF, отсортированный
   `lock.json`, без дат. Если две ветки независимо обновились до одной версии, git сливает их без
   конфликтов (это проверяется тестом).
3. **Локальные правки не теряются молча.** `lock.json` хранит хэши всего, что записала платформа.
   Если файл платформы или управляемый блок правили руками, установщик останавливается до записи
   и показывает список. С `--force` он сохраняет копии в `.ludovanta-backup/<время>/` и перезаписывает.
4. **Удалённое из платформы удаляется из проекта**, но только если файл не меняли локально.
5. **Конфликты чинятся регенерацией.** Если ветки обновились до разных версий и файлы платформы
   конфликтуют, руками их не разрешают: выберите версию в `ludovanta.json` и запустите `update --force`.
   Повреждённые маркерами конфликта блоки и `lock.json` перегенерируются.
6. **Переводы строк и кодировки.** Управляемый блок `.gitattributes` фиксирует `eol=lf` для файлов
   платформы, а установщик сохраняет CRLF/LF, BOM и байты в ваших общих файлах как есть.
7. **Никакого мусора от Python.** Команды не создают `__pycache__` в `.ludovanta/`, а на всякий случай он
   добавлен в `.gitignore`-блок.
8. **Хуки в `.claude/settings.json`.** Платформе принадлежат только обработчики, которые запускают
   `.ludovanta/hook.sh`: при обновлении они удаляются и добавляются заново, остальные настройки и хуки не
   трогаются. Битый JSON останавливает установку до записи.

### Как кастомизировать, не ломая обновления

- Свои инструкции и настройки: в `AGENTS.md` вне блока `ludovanta:managed` (их видят и Claude, и Codex).
- Свои скиллы: папки без префикса `ludovanta-`.
- Путь к Unity на конкретной машине: `ludovanta.local.json` → `{ "unityEditorPath": "D:/Unity/6000.0.30f1/Editor/Unity.exe" }`
  (на macOS можно указать `.app`) или переменная окружения `UNITY_EDITOR_PATH`.
- Папки для скиллов агентов: `ludovanta.json` → `"skillTargets"` (по умолчанию `[".claude/skills", ".agents/skills"]`),
  затем `update`. Убранная из списка папка будет очищена от `ludovanta-*`.

## Режимы работы агентов

- **HEADLESS** (Editor не открыт; типичный случай для параллельных агентов в своих worktree):
  `compile`/`test` запускают Unity в batchmode.
- **LIVE** (проект открыт в Unity Editor): второй экземпляр Unity на ту же папку запустить нельзя,
  команды возвращают `EDITOR_OPEN` (код 3), и агент работает через официальный Unity MCP
  (пакет `com.unity.ai.assistant`). Включайте MCP только агенту, который работает в папке
  открытого Editor: relay подключается к открытому Editor, а не к worktree агента.

Открытый проект определяется по `Temp/UnityLockfile`: на Windows через эксклюзивное открытие файла,
на macOS/Linux через `flock`/`lockf` и поиск процесса с `-projectPath <проект>`. Оставшийся после
падения Editor lock-файл открытым проектом не считается.

## Разработка платформы

```
install.py               # установщик/обновлятор (запускается из нужной версии платформы)
VERSION                  # версия платформы (semver)
payload/files/           # копируется в проект как есть (.ludovanta/...)
payload/skills/          # копируется в каждую папку из skillTargets
payload/blocks/          # содержимое управляемых блоков для общих файлов
tests/                   # pytest: установщик, команды (с фейковым Unity), парсеры
pyproject.toml           # настройки pytest
requirements-dev.txt     # зависимости для разработки платформы (pytest)
```

- Тесты (pytest нужен только для разработки платформы, в игровые проекты он не попадает):

  ```
  python3 -m venv .venv
  .venv/bin/pip install -r requirements-dev.txt        # Windows: .venv\Scripts\pip ...
  .venv/bin/python -m pytest
  ```

  или без venv через uv: `uv run --with-requirements requirements-dev.txt pytest`.
- Unity для тестов не нужен: `tests/fake_unity.py` изображает batchmode Unity (лог, результаты
  тестов, ошибки компиляции, проблему с лицензией), поэтому тесты можно гонять в CI на любой ОС.
  Фикстуры (проект, установленная платформа, git-origin с тегами, удерживаемый lock-файл Unity)
  лежат в `tests/conftest.py`.
- Проверка на живом проекте без релиза: укажите в его `ludovanta.json` `"source"` как путь к локальной
  папке платформы, тогда `update` берёт рабочую копию как есть.
- Релиз: поднять `VERSION`, закоммитить, поставить тег `vX.Y.Z` и запушить тег.
- Код в `payload` использует только стандартную библиотеку и должен работать на Python 3.9.
